## 검토 개요 (Executive Overview)

### 검토 대상
ReGrip — 손 재활 게이미피케이션 웹앱. O2O 구조(오프라인 FSR 악력 센서 하드웨어 + 온라인 웹앱)를 지향하는 재활 의료 인접(medical-adjacent) 서비스. 현재 산출물은 다음으로 구성된 정적 프로토타입이다.

- HTML 10종: `index.html`, `training.html`, `history.html`, `achievements.html`, `settings.html`, `profile.html`, `level.html`, `calibration.html`, `game-balloon.html`, `game-crane.html`
- 공용 스크립트 `shared.js` (`DataService` / `SensorService` / 내비게이션 / 목데이터 시더)
- 공용 스타일 `shared.css` (네오 레트로 디자인 시스템)
- Tailwind CDN, localStorage 저장소, 백엔드 미구축 (`DataService`에 REST 전환 초안만 존재)

### 검토 범위
1. **UI/UX 및 사용자 여정** — 인터랙션 결함, 접근성(WCAG), 임상적 피드백 정합성, 온보딩/빈 상태 설계
2. **백엔드 로직 및 DB 아키텍처 준비도** — 서비스 계층 추상화 완성도, 센서 통신 계층, 백엔드/데이터 모델 설계 성숙도
3. **시스템 데이터 정합성 (Front-to-Back 교차 검증)** — 프론트가 표시하는 값과 실제 데이터 소스 간의 논리적 정합성, 게임 결과와 게이미피케이션 지표의 인과 연결

### 방법론
- 정적 코드 감사(static code audit): 전체 HTML/JS/CSS 라인 단위 판독
- 데이터 흐름 추적(data-flow tracing): 게임 세션 저장 → 저장소 → 각 소비 페이지까지의 필드 계보(lineage) 추적
- 스키마 정합성 대조: 생산 측 스키마(게임 저장) vs 소비 측 기대 스키마(history/profile/achievements)
- 접근성 정량 평가: WCAG 2.1 AA 명암비 계산, 키보드 내비게이션/모션 정책 확인
- Best Practice 대조: REST 클라이언트 설계, 실시간 소켓 재연결 패턴, 게이미피케이션 서버 권위(server authority) 원칙

본 검토는 **코드로 실증된 결함만** 근거로 삼는다. 모든 쟁점에 `파일:라인` 근거를 명시했다. 추정·인상 평가는 배제했다.

### 종합 판정 (Verdict)

디자인 시스템의 완성도와 시뮬레이션 우선(simulation-first) 설계 감각은 프로토타입 수준을 상회한다. 그러나 **제품의 심장인 "게임을 하면 내 재활 지표가 성장한다"는 인과 루프가 코드상 전혀 연결되어 있지 않다.** 화면에 보이는 레벨·XP·연속출석·배지·진행률은 모두 인라인 상수 또는 `Math.random` 목데이터이며, 게임 결과와 아무 관계가 없다. 이 상태는 "재활 성과 게이미피케이션"이라는 제품 정의 자체가 아직 존재하지 않음을 의미한다.

따라서 본 검토의 결론은 명확하다. **UI 스킨은 8부 능선을 넘었으나, 제품의 논리적 골격(도메인 엔진 + 백엔드 권위)은 0부 능선이다.** 지금 필요한 것은 화면을 더 그리는 일이 아니라, 단일 진실 소스(Single Source of Truth) 위에 게이미피케이션 엔진과 백엔드 권위 계층을 세우는 일이다.

## 1. UI/UX 디자인 및 사용자 여정 검토 결과

디자인 시스템 자체는 강점이나(1.6 참조), 인터랙션 계층에 명백한 상태 관리 버그가 있고, **재활 의료 도메인에서 용납되기 어려운 임상적 피드백 오류와 접근성 결함**이 존재한다. 재활 서비스는 일반 소비자 앱과 달리 "잘못된 피드백"이 곧 "잘못된 운동 처방"이 되므로, 이 영역의 결함은 등급을 상향해 다룬다.

### 1.1 [UX-1 · Medium] history 탭 전환 상태 관리 버그

* **발견된 쟁점:**
  `history.html`의 `switchTab()`(`:214-225`)이 **비활성 탭에만 인라인 스타일**(`btn.style.background = '#fff'` 등, `:220-222`)을 직접 주입하고, 활성 탭으로 복귀할 때 그 인라인 스타일을 **되돌리지 않는다.** 결과적으로 "기록 → 통계 → 기록" 왕복 시, 한 번 비활성화되며 `#fff` 인라인 배경이 박힌 탭이 다시 활성화되어도 인라인 스타일이 `.tab-btn.active` 클래스 규칙을 CSS 명시도(specificity)에서 이겨, **활성 탭이 흰색으로 잘못 표시**된다.

* **기술적/경험적 분석:**
  전형적인 명령형 DOM 조작의 상태 누수(state leak)다. 인라인 스타일은 클래스 셀렉터보다 명시도가 높기 때문에, 상태를 인라인으로 켰다면 상태 전환 시 반드시 인라인으로 꺼야 한다. 현재 코드는 "켜기"만 있고 "끄기"가 없다. 이는 스타일링을 명령형(JS가 색을 직접 지정)과 선언형(CSS 클래스)으로 **이중 관리**한 데서 비롯된 구조적 결함이며, 다른 페이지에도 동일 패턴(`calibration.html`의 버튼 직접 스타일링 `:167-218` 등)이 산재해 향후 같은 부류의 버그가 재발할 소지가 크다.

* **개선 솔루션:**
  1. **인라인 스타일 전면 제거**, 상태는 오직 클래스로 표현한다.
     ```js
     function switchTab(name) {
       ['log', 'stats'].forEach(t => {
         const active = t === name;
         document.getElementById(`content-${t}`).classList.toggle('active', active);
         document.getElementById(`tab-${t}`).classList.toggle('active', active);
       });
     }
     ```
     활성/비활성 스타일은 `.tab-btn`, `.tab-btn.active` 두 규칙으로만 정의한다.
  2. 근본 처방: 프로젝트 전역에서 **"JS는 클래스만 토글, 색·그림자는 CSS가 소유"** 규칙을 컨벤션으로 명문화한다. 이는 UX-1뿐 아니라 캘리브레이션·게임 결과 화면의 유사 결함을 예방한다.

### 1.2 [UX-2 · High] 풍선 게임 — 게이지 목표존과 물리 평형점 불일치 (임상적 오피드백)

* **발견된 쟁점:**
  풍선 게임은 사용자에게 **게이지 목표존을 50~70%로 시각 표시**한다(`game-balloon.html:273-274`: 주석 `We show gauge zone for 50-70% roughly`, `gaugeTarget.style.bottom = '50%'`). 그러나 실제 풍선을 움직이는 물리식은
  ```js
  const velocity = (gripForce - 30) * 0.08;  // neutral at 30%   (:367)
  ```
  로, **풍선이 정지(평형)하는 지점은 악력 30%**다. 즉 사용자가 화면이 지시하는 50~70%로 힘을 주면 풍선은 계속 상승해 이탈하고, 실제로 풍선을 목표 높이에 "유지"하려면 화면과 무관하게 30% 근방을 유지해야 한다. **화면이 요구하는 힘과 게임이 보상하는 힘이 40%p 어긋나 있다.**

* **기술적/경험적 분석:**
  일반 게임이라면 밸런스 버그로 그치지만, ReGrip은 **재활 환자에게 특정 악력 세기를 유지하도록 훈련시키는 의료 인접 도구**다. 목표존 표시는 사실상 "이만큼 힘을 주라"는 **운동 처방(prescription)**으로 기능한다. 따라서 이 불일치는 단순 UX 버그가 아니라 **잘못된 운동 강도를 지시하는 임상적 오피드백**이며, 재활 효과 저하·과사용 손상·환자 신뢰 붕괴로 직결될 수 있다. 재활 도메인에서 피드백 정합성은 기능 정확도가 아니라 **안전 요건**이다.

* **개선 솔루션:**
  1. **물리식과 목표존을 단일 파라미터에서 파생**시켜 구조적으로 어긋날 수 없게 한다. 예: 목표 유지 악력 `TARGET_HOLD`를 상수로 두고, 평형점과 게이지존을 모두 이 값에서 계산한다.
     ```js
     const TARGET_HOLD = 60;          // 임상적으로 결정된 목표 유지 악력(%)
     const velocity = (gripForce - TARGET_HOLD) * 0.08;   // 평형점 = TARGET_HOLD
     gaugeTarget.style.bottom = `${TARGET_HOLD - BAND/2}%`;
     gaugeTarget.style.height = `${BAND}%`;               // 시각 목표존도 동일 소스
     ```
  2. `TARGET_HOLD`·`BAND`(허용 오차 밴드)는 **캘리브레이션 결과와 재활 단계**에 따라 주입받도록 설계한다(UX-5·DI-7과 연동). 목표 악력은 환자마다 달라야 하며 하드코딩 상수여선 안 된다.
  3. 임상 파라미터(목표 강도·유지 시간·허용 오차)는 **재활 전문가 검수를 거친 값**으로 확정하고, 코드가 아닌 설정 데이터로 관리한다.

### 1.3 [UX-3 · High] 접근성(WCAG 2.1 AA) 다중 미달 — 재활 사용자 특성상 등급 상향

* **발견된 쟁점:** 다음이 코드/토큰으로 확인된다.
  - **명암비 미달:** `--ink-muted` `#94A3B8`는 흰 배경 대비 **약 2.6:1**로 본문 텍스트 기준 4.5:1(WCAG AA)에 크게 미달. success 텍스트 `#16A34A`도 흰 배경 대비 **약 3.3:1**로 본문 미달. 이 색들은 부가 정보가 아니라 상태·수치 표기에 쓰이고 있다.
  - **키보드 접근성 부재:** `:focus-visible` 스타일이 전역에 **전무** → 키보드 내비게이션 시 초점 위치가 보이지 않는다. 클릭 카드가 `div onclick`으로 구현되어(예: history 세션 카드, 홈 진입 카드) **키보드/스크린리더로 진입 불가**.
  - **모션 정책 부재:** `prefers-reduced-motion` 대응이 **전무**하여 `cloudDrift`, `pulse` 등 무한 애니메이션이 항상 구동된다.
  - **터치 타깃 부족:** 모바일 하단 탭바(`nav-bottom-item`)의 터치 영역이 권장치(최소 44×44pt) 대비 부족.
  - **네이티브 `confirm()` 사용:** 게임 종료 확인에 브라우저 기본 `confirm()`을 사용해 디자인·접근성·모바일 UX 일관성이 깨진다.

* **기술적/경험적 분석:**
  일반 앱에서 접근성은 규정 준수 항목이지만, ReGrip의 사용자군은 **손 기능이 저하된 재활 환자, 고령자, 잠재적 전정장애/광과민 사용자**를 포함한다. 이 집단에서:
  - 낮은 명암비는 시력 저하 사용자에게 **정보 판독 실패**를 유발한다.
  - 무한 애니메이션은 **전정장애·광과민 사용자에게 어지럼/불편**을 유발할 수 있고, 재활 집중을 방해한다.
  - 초점 미표시·`div onclick`은 **키보드 전용/보조기기 사용자를 배제**한다. 손 기능 저하 사용자가 오히려 키보드/스위치 접근에 의존할 수 있다는 점에서 치명적이다.

  즉 접근성 결함이 곧 **핵심 타깃 사용자 배제**로 직결되므로, 일반적 Medium을 High로 상향한다. 다수 국가에서 의료/공공 성격 서비스는 접근성 준수가 법적 요건이기도 하다.

* **개선 솔루션:**
  1. **디자인 토큰 명암비 재조정:** 본문에 쓰이는 muted/success 계열 색을 AA(본문 4.5:1, 대형 텍스트 3:1) 충족 값으로 상향. 예: muted를 `#64748B`(대비 ≈ 4.6:1)로, success 텍스트를 `#15803D` 이상으로. 색 자체 대신 아이콘·굵기 등 **비색 신호를 병행**한다.
  2. **전역 `:focus-visible` 스타일** 도입:
     ```css
     :focus-visible { outline: 3px solid var(--primary); outline-offset: 2px; border-radius: 4px; }
     ```
  3. **클릭 요소를 시맨틱 요소로 전환:** `div onclick` → `<button>` 또는 `<a>`. 불가피하면 `role`, `tabindex="0"`, 키다운 핸들러를 갖춘 접근성 래퍼 유틸을 `shared.js`에 둔다.

### 1.4 [UX-4 · Medium] 빈 상태(Empty State)·온보딩 미설계

### 2.1 [BE-1 · High] `DataService` REST 전환 미완 — 부분 우회, 인증·에러·멱등성 전무

* **발견된 쟁점:**
  `DataService`(`shared.js:119-177`)는 `local`/`rest` 백엔드 전환을 표방하나, 다음의 구조적 결함이 있다.
  1. **엔드포인트 4개뿐:** `GET/PUT /api/profile`, `GET/POST /api/sessions`만 존재. 캘리브레이션·게이미피케이션·업적 등 도메인 대부분이 미커버.
  2. **동기 프로필 조회에 REST 분기 없음:** `getProfileSync()`(`:129-132`)는 항상 localStorage를 읽는다. 그런데 내비게이션(`injectNav`, `:17`)이 이 동기 함수로 사용자 이름·아바타를 그린다 → **REST 모드에서도 nav의 사용자 정보는 서버가 아닌 로컬을 본다.**
  3. **레거시 경로가 서비스 계층을 우회:** `loadSessions()`(`:255`)가 localStorage를 직접 읽고, `history.html:460`·`profile.html:275`가 이 레거시 함수를 사용한다 → **REST 모드에서 기록/프로필의 세션이 서버에서 로드되지 않는다.**
  4. **설정·캘리브레이션은 `DataService`를 완전 우회**하고 localStorage에 직접 붙는다.
  5. **네트워크 위생 전무:** 모든 `fetch`에 **인증 헤더 없음**, `res.ok` 검사 없음, `try/catch` 없음, **타임아웃 없음**. 서버 에러/네트워크 단절 시 조용히 깨지거나 `undefined`가 전파된다.
  6. **멱등성 부재:** 로컬 `saveSession`이 `id = Date.now()`를 **클라이언트에서 생성**(`:173`) → 중복 제출/재시도 시 **중복 세션 저장**. REST 전환 시 이 문제는 서버 데이터 오염으로 확대된다.

* **기술적 분석:**
  이 추상화는 "나중에 `setBackend('rest')` 한 줄이면 서버로 전환된다"는 약속을 표방하지만, **실제로는 절반만 서버로 가고 절반은 로컬에 남는 하이브리드 오작동**을 낳는다. 이는 가장 위험한 종류의 결함이다 — 컴파일 에러처럼 즉시 터지지 않고, 전환 후 "일부 데이터만 동기화되는" 형태로 **조용히** 나타나기 때문이다. 또한 인증·에러·타임아웃·멱등성은 REST 클라이언트의 **선택 사항이 아니라 기본 요건**이다. 특히 세션 저장의 멱등성 부재는 재활 데이터의 신뢰도(예: "오늘 몇 번 훈련했나")를 직접 훼손한다.

* **개선 솔루션:**
  1. **단일 게이트웨이 강제:** 모든 데이터 접근을 `DataService`로 일원화한다. `loadSessions()` 레거시 및 페이지의 localStorage 직접 접근(설정·캘리브레이션 포함)을 **전부 `DataService` 경유로 교체**하고, `getProfileSync`는 로컬 캐시 + 비동기 갱신(stale-while-revalidate) 패턴으로 정리해 REST 모드 정합을 맞춘다.
  2. **공통 fetch 래퍼:** 인증 헤더 주입, `res.ok` 검사, `AbortController` 타임아웃, `try/catch` + 표준 에러 객체, 재시도(지수 백오프)를 한 곳에서 처리.
     ```js
     async _request(path, { method='GET', body, idempotencyKey } = {}) {
       const ctl = new AbortController();
       const t = setTimeout(() => ctl.abort(), 10000);
       try {
         const res = await fetch(`${this._baseUrl}${path}`, {
           method,
           headers: {
             'Content-Type': 'application/json',
             ...(this._token && { Authorization: `Bearer ${this._token}` }),
             ...(idempotencyKey && { 'Idempotency-Key': idempotencyKey }),
           },
           body: body && JSON.stringify(body),
           signal: ctl.signal,
         });
         if (!res.ok) throw new ApiError(res.status, await res.text());
         return res.status === 204 ? null : res.json();
       } finally { clearTimeout(t); }
     }
     ```
  3. **멱등성 키:** 세션 저장 시 클라이언트가 `crypto.randomUUID()`로 **멱등키를 생성해 헤더로 전달**하고, **서버가 최종 ID를 발급**한다(`Date.now()` 클라 ID 폐기). 서버는 동일 멱등키 재수신 시 기존 리소스를 반환한다.
  4. 이 계약은 아래 BE-4의 API 명세와 함께 확정한다. (참고: `docs/backend/00~07` 설계서가 본 검토와 함께 신규 작성됨 — 해당 명세를 SSOT로 사용)

### 2.2 [BE-2 · High] `SensorService` 재연결 로직 사문화 · `connect()` 미호출

* **발견된 쟁점:**
  두 개의 독립된 결함이 겹쳐 있다.
  1. **재연결 조건 논리 오류:** `onerror` 핸들러가 `this._mode = 'simulation'`으로 설정한다(`:216-219`). 그런데 직후 실행되는 `onclose` 핸들러의 자동 재연결 조건은 `if (this._mode === 'websocket')`이다(`:221-225`). 소켓 에러로 끊길 때는 `onerror` → `onclose` 순으로 불리므로, `onclose` 시점엔 이미 mode가 `simulation`으로 바뀌어 있어 **재연결 분기에 진입하지 못한다.** 즉 정상 종료가 아닌 **에러 단절 시 3초 재시도 로직이 절대 발동하지 않는다.** 재연결 로직이 코드로만 존재하는 사문(死文)이다.
  2. **`connect()`가 어디서도 호출되지 않음:** 전체 HTML 어디에서도 `SensorService.connect(...)`를 호출하지 않는다(`:196`). 게임들은 시뮬레이션 경로(`setSimulatedForce`)로만 힘을 주입한다. **앱은 항상 시뮬레이션 모드로만 동작하며, 실제 하드웨어에 연결되는 경로가 존재하지 않는다.**

* **기술적 분석:**
  ReGrip의 제품 정의는 O2O — 실제 FSR 센서 연결이 핵심이다. 그런데 하드웨어 연결 진입점 자체가 코드에 없고, 있다 해도 재연결이 사문화되어 있다. 실시간 소켓 통신에서 재연결은 필수 신뢰성 요건인데, 상태 플래그를 재연결 조건과 부작용(fallback)에 **이중 용도로 사용**한 설계 오류가 그 요건을 무너뜨렸다. 이는 상태 머신을 명시적으로 모델링하지 않고 단일 플래그로 여러 의미(현재 전송원 / 연결 의도 / 재연결 여부)를 겹쳐 표현한 데서 비롯됐다.

* **개선 솔루션:**
  1. **의도와 상태를 분리:** "연결을 원하는가"(`_shouldConnect`)와 "현재 전송원"(`_mode`)을 다른 변수로 둔다. 재연결 여부는 `_mode`가 아니라 `_shouldConnect`로 판단한다.
     ```js
     this._ws.onclose = () => {
       if (this._shouldConnect) {
         this._reconnectTimer = setTimeout(() => this.connect(this._wsUrl), this._backoff());
       } else { this._mode = 'simulation'; }
     };
     ```
     `onerror`는 로깅만 하고 mode를 바꾸지 않는다(닫힘은 `onclose`가 판정). 재시도에는 지수 백오프 + 지터를 적용한다.
  2. **연결 진입점 배선:** 훈련/게임 시작 시(또는 설정에서) `SensorService.connect(url)`을 호출하고, 실패/미연결 시 명시적으로 시뮬레이션 모드로 폴백하는 UX(BE-3의 실제 상태 표시와 연동)를 둔다.
  3. 장기적으로 WebSocket 외 **Web Serial / Web Bluetooth** 경로도 이 서비스 뒤로 추상화해 하드웨어 연결 방식을 캡슐화한다.

### 2.3 [BE-3 · Medium] 센서 상태 표시 상호 모순 (하드코딩)

* **발견된 쟁점:**
  내비 사이드바는 **"센서 연결됨" + 초록 인디케이터**를 하드코딩으로 표시한다(`shared.js:44-50`: 초록 아이콘 색 `#16A34A`, 초록 점). 반면 게임 헤더는 **"시뮬레이션" 배지**를 하드코딩으로 표시한다(예: `game-balloon.html:84` 부근의 초록 점 + 상태 라벨). 둘 다 실제 `SensorService.getMode()` 상태를 반영하지 않으며, **서로 모순**된다(한쪽은 "연결됨", 다른 쪽은 "시뮬레이션").

* **기술적 분석:**
  상태 표시가 실제 상태의 **파생값이 아니라 장식**이다. 재활 기기 앱에서 "센서 연결 상태"는 데이터 신뢰성의 근거이므로 정확해야 한다. 사용자가 "연결됨"을 믿고 훈련했는데 실제로는 시뮬레이션 난수였다면, 기록된 악력 데이터 전체가 신뢰를 잃는다.

* **개선 솔루션:**
  1. **단일 상태 소스 구독:** 모든 센서 상태 UI는 `SensorService.getMode()` / 연결 이벤트를 구독해 렌더한다. 서비스에 `onStatusChange(cb)`를 추가하고, nav와 게임 헤더가 이를 동일하게 구독한다.
  2. 상태를 최소 3종(연결됨 / 시뮬레이션 / 연결 끊김·재시도 중)으로 모델링하고, 색·라벨·아이콘을 상태에서 파생한다. 하드코딩 제거.

### 2.4 [BE-4 · Critical] 백엔드/DB 설계 부재 — ERD·API·인증·트랜잭션·개인정보

* **발견된 쟁점:**
  백엔드를 향한 코드 초안(`DataService`)은 있으나, 그 초안이 대화할 **서버·데이터 모델·계약이 설계되지 않았다.** 구체적으로 다음이 미검토·미문서화 상태다.
  - **ERD/데이터 모델 부재:** 사용자·프로필·세션·세트·업적·XP·캘리브레이션의 관계와 스키마가 정의되지 않음.
  - **API 명세 부재:** 엔드포인트·요청/응답 계약·에러 코드·버저닝 미정.
  - **인증·인가 부재:** 회원/세션/토큰 모델 없음(BE-1의 인증 헤더 부재와 직결).
  - **트랜잭션 원자성 미설계:** 세션 저장 → XP 적립 → 업적 판정이 **하나의 원자적 트랜잭션**으로 처리되어야 하나(부분 반영 시 지표 붕괴), 이 경계가 정의되지 않음.
  - **서버 권위(server authority) 부재:** `stars`·XP를 **클라이언트가 계산**해 그대로 신뢰하는 구조 → **치팅에 무방비**. 재계산은 서버가 해야 한다.
  - **개인정보/규제:** 재활 데이터는 **건강정보(민감정보)**로, 개인정보보호법상 별도 동의·보호 조치 대상일 수 있음. 이에 대한 설계·동의 플로우 미검토.
  - **바이너리 저장 오설계 위험:** `avatarBase64`를 DB에 그대로 저장하면 로우 비대화·성능 저하 → **오브젝트 스토리지로 분리**하고 DB엔 URL만 저장해야 한다.

* **기술적 분석:**
  이것이 프로젝트 최대의 Critical이다. 게이미피케이션 지표(레벨/XP/업적)를 클라이언트가 계산·저장하도록 두면, 값의 **권위 소재(authority)**가 브라우저에 있게 되어 조작이 자명해지고(치팅), 기기·페이지 간 정합도 무너진다. 게다가 "세션 저장 → XP 적립 → 업적 판정"은 반드시 원자적이어야 한다 — 세션은 저장됐는데 XP는 안 붙거나, 업적만 붙는 부분 실패는 그대로 지표 모순(섹션 3의 재발)을 만든다. 백엔드는 "나중에 붙이는 저장소"가 아니라 **게이미피케이션의 권위와 정합성을 책임지는 계층**이며, 이 설계가 없으면 섹션 3의 데이터 모순은 서버로 옮겨가 재생산될 뿐이다.

* **개선 솔루션(스키마/API 방향):**
  1. **관계형 DB(PostgreSQL) 모놀리식**으로 시작한다(초기 규모에 적합, 트랜잭션·정합성 강점). 핵심 스키마 방향:
     ```
     users(id, email, auth_provider, created_at, ...)
     profiles(user_id PK/FK, name, hand, avatar_url, rehab_stage, ...)   -- avatar는 URL만
     calibrations(id, user_id, baseline_min, baseline_max, captured_at)  -- DI-7 저장 대상
     sessions(id, user_id, game_type, label, started_at, duration_min,
              avg_force, max_force, stars, idempotency_key UNIQUE, ...)  -- 멱등키 유니크
     session_sets(id, session_id FK, set_num, reps, hold_time, force)    -- DI-6: 실제 세트 영속화
     xp_ledger(id, user_id, session_id FK, delta, reason, created_at)    -- XP는 원장(append-only)
     achievements(user_id, achievement_key, unlocked_at)                 -- 상태가 아닌 이력
     ```
     레벨·현재 XP·연속출석은 **저장 컬럼이 아니라 원장/세션에서 파생 계산**하거나, 성능 위해 파생값을 캐시하되 **원천은 원장**으로 둔다.
  2. **세션 제출 = 단일 트랜잭션:** `INSERT session → INSERT xp_ledger → UPSERT achievements`를 하나의 트랜잭션으로 처리하고, `stars`·XP는 **서버가 세션 원시값으로부터 재계산**한다(클라 값 불신).
  3. **인증:** JWT 기반(액세스+리프레시), 모든 데이터 엔드포인트에 인가 적용.
  4. **개인정보:** 건강정보 취급 방침·수집 동의 플로우·암호화/접근통제·보관기간을 설계에 포함. 아바타 등 바이너리는 오브젝트 스토리지 분리.
  5. **참고 문서:** 본 검토와 함께 신규 작성된 `docs/backend/00~07` 설계서(PostgreSQL 모놀리식, JWT, 세션 저장 단일 트랜잭션 + 멱등키, stars/XP 서버 재계산)를 착수 전 확정 기준(baseline)으로 채택한다.

### 3.1 [DI-1 · Critical] 게이미피케이션 지표 전면 하드코딩 — 게임 결과와 완전 무관

* **논리적 충돌 및 간극:**
  레벨·XP·연속출석·배지·주간 목표·진행률 등 게이미피케이션 지표 **전부**가 각 페이지에 **인라인 상수로 박제**되어 있으며, 게임 플레이 결과와 아무 연결이 없다. 확인된 하드코딩:
  - `index.html`: Lv.12/초심자(`:55-56`), 연속출석 7일(`:96`), 주간 +12%(`:105`), 배지 3/5(`:114`), 주간목표 5/7일·71%(`:123-126`), 최근 세션 2건(`:135-155`)
  - `level.html`: `CURRENT_LEVEL = 12`(`:334`), `XP_HISTORY` 8건(`:359-368`), `TIERS`(`:325-332`)
  - `achievements.html`: `ACHIEVEMENTS` 5종(`:253-319`), 3/5(`:133`)
  - `profile.html`: Lv.12 · 850XP · 62%(`:141-146`), 배지 3(`:159`)

  이 모든 값은 **정적**이다. 사용자가 게임을 100번 하든 0번 하든 화면은 "Lv.12, 연속출석 7일, 배지 3/5"로 고정된다.

* **기술적 분석:**
  이것은 "버그"가 아니라 **제품 핵심 기능의 부재**다. ReGrip의 존재 이유는 "재활 훈련 성과를 게이미피케이션으로 시각화·동기부여"하는 것인데, 그 게이미피케이션이 실제 성과의 **함수가 아니라 상수**다. 데이터 아키텍처 관점에서 이는 **파생 상태(derived state)를 원천 데이터로부터 계산하지 않고, 화면마다 별도로 하드코딩한** 근본적 설계 부재다. 하드코딩이 여러 페이지에 흩어져 있으므로 필연적으로 서로 모순되고(DI-2), 게임 결과를 반영할 방법도 없다(DI-3). 이 상태로는 **데모는 되지만 제품은 아니다.**

* **통합 개선안:**
  1. **단일 진실 소스 게이미피케이션 엔진 도입:** 레벨·XP·연속출석·배지·진행률을 **세션 데이터로부터 파생 계산**하는 순수 함수 계층(`GamificationService`)을 만든다. 모든 페이지는 이 엔진의 계산 결과만 렌더하고, 인라인 상수를 전량 제거한다.
     ```js
     const GamificationService = {
       computeStats(sessions, achievements) {
         const totalXp = sessions.reduce((s, x) => s + this.xpForSession(x), 0)
                       + achievements.reduce((s, a) => s + a.xp, 0);
         const level = this.levelForXp(totalXp);          // TIERS 단일 정의
         const streak = this.computeStreak(sessions);     // 날짜 기반 실계산 (SSOT)
         const progress = this.progressToNext(totalXp, level);
         return { totalXp, level, streak, progress, badgeCount: this.badges(achievements) };
       },
       // xpForSession, levelForXp, computeStreak, progressToNext ...
     };
     ```
  2. **`TIERS`·XP 곡선·업적 정의를 단일 모듈로 통합**해 페이지별 중복을 제거한다.
  3. 최종적으로 이 계산의 **권위는 서버**(BE-4)가 갖고, 클라이언트 엔진은 표시용 미러로 둔다.
  4. 착수 우선순위 최상위(섹션 4-1).

### 3.2 [DI-2 · High] 페이지 간 수치 상호 모순 · 내부 산수 모순 · 연도 혼재

* **논리적 충돌 및 간극:** DI-1의 필연적 결과로, 하드코딩된 값들이 서로 어긋난다.
  - **연속출석 3중 모순:** `index.html`=7일(하드코딩), `history.html`=실계산(목데이터 기준 **14일**), `achievements.html`="7일 연속" 문구. 같은 지표가 화면마다 7·14·7로 다르다.
  - **`level.html` 내부 산수 모순:** 2,150 / 3,000 XP인데 진행률을 **62%**로 표기(실제 71.7%). 남은 XP를 850(28.3%)로 표기해 62% 표기와도 상호 모순(62%면 남은 것이 38%여야 함).
  - **연도 혼재:** 업적 획득일이 **2023년**인데 목 세션 날짜는 **2026년**(현재 기준). 동일 사용자 이력의 시간축이 3년 어긋난다.

* **기술적 분석:**
  이 모순들은 개별 오탈자가 아니라 **SSOT 부재의 증상**이다. 하나의 지표(연속출석, 진행률)를 여러 곳에서 독립적으로 하드코딩하면 반드시 발산한다. 특히 진행률 62%는 2,150/3,000의 어떤 해석과도 맞지 않아, 값들이 서로 다른 시점에 임의로 채워졌음을 보여준다. 사용자 관점에서 이 모순은 즉시 감지 가능하며 **제품 신뢰도를 결정적으로 훼손**한다(재활 데이터를 믿을 수 없다는 인상).

* **통합 개선안:**
  DI-1의 `GamificationService`가 근본 해법이다. 모든 수치가 단일 계산에서 나오면 정의상 모순이 불가능하다. 진행률은 `(현재XP - 레벨하한) / (레벨상한 - 레벨하한)`로 일관 계산하고, 날짜는 세션의 실제 타임스탬프에서만 파생한다. 업적 획득일도 실제 달성 시각으로 기록(BE-4의 `achievements.unlocked_at`)해 연도 혼재를 제거한다.

### 3.3 [DI-3 · Critical] XP 부여(적립) 코드 자체가 부재

* **논리적 충돌 및 간극:**
  세션을 저장할 때(`DataService.saveSession`)도, 업적을 달성할 때도, 앱 **어디에도 XP를 적립하는 로직이 없다.** 게임 결과 → XP 증가 → 레벨업이라는 **인과 사슬의 첫 고리가 아예 존재하지 않는다.** XP/레벨 시스템은 순수 장식이다.

* **기술적 분석:**
  DI-1이 "표시가 하드코딩"이라면, DI-3은 그보다 근본적인 "**적립 이벤트 자체의 부재**"다. 설령 표시를 파생 계산으로 바꿔도(DI-1 해결), 세션이 XP를 발생시키지 않으면 계산할 원천 데이터가 없다. 즉 DI-3은 DI-1의 **선결 조건**이다. 게이미피케이션의 최소 단위 이벤트("이 행동이 이만큼의 XP를 준다")가 정의·기록되지 않는 한, 어떤 표시도 진짜일 수 없다.

* **통합 개선안:**
  1. **적립 규칙 정의:** "세션 완료 = f(duration, avgForce, maxForce, stars) XP", "업적 달성 = 고정 XP" 등 규칙을 명시한다.
  2. **적립 이벤트를 데이터로 기록:** 세션 저장 시 XP 원장(`xp_ledger`, BE-4)에 append. 로컬 단계에서도 최소한 세션에서 파생 계산이 가능하도록 규칙을 순수 함수로 둔다.
  3. **원자성 보장:** 세션 저장과 XP 적립·업적 판정은 하나의 트랜잭션(서버) / 하나의 커밋(로컬)으로 묶어 부분 반영을 배제한다(BE-4).
  4. 서버 권위로 재계산해 치팅을 방지한다.

### 3.4 [DI-4 · Medium] `hand`(주 사용손) 이중 소스, 동기화 없음

* **논리적 충돌 및 간극:**
  주 사용손 정보가 **두 개의 저장 키에 별도로 존재**한다. `regrip_profile.hand`(`profile.html:286`, `:328`)와 `regrip_settings.hand`(`settings.html:265`, `:267`)가 서로 **동기화되지 않는다.** 한쪽에서 바꿔도 다른 쪽은 옛 값을 유지한다.

* **기술적 분석:**
  동일 개념(사용자의 재활 대상 손)이 두 소스에 중복되어 발산할 수 있는 전형적 정합성 결함이다. 캘리브레이션·게임이 어느 값을 신뢰해야 하는지 불명확하고, 사용자가 "설정에서는 왼손, 프로필에서는 오른손"인 모순 상태에 빠질 수 있다. 재활 대상 손은 데이터 해석의 기준이므로 사소하지 않다.

* **통합 개선안:**
  `hand`의 **소유를 프로필로 단일화**하고(도메인상 프로필이 사용자 정체성 정보의 소유자), 설정 화면은 프로필 값을 읽고 쓰는 뷰로 만든다. 저장 키를 하나(`regrip_profile.hand`)로 통합하고, BE-4 스키마에서 `profiles.hand` 단일 컬럼으로 확정한다.

### 3.5 [DI-5 · High] `seedMockData` 자동 주입 — 실/목 혼입 · 삭제 무력화 · 어휘 불일치

* **논리적 충돌 및 간극:**
  `seedMockData()`(`shared.js:258-274`)가 세션 0건일 때 **14일치 `Math.random` 목데이터를 자동 주입**하며, 이 함수는 `initPage()`(`:293`)에서 **모든 페이지 로드마다 호출**된다. 여기서 세 가지 결함이 파생된다.
  1. **실/목 혼입:** 실제 사용자 세션과 난수 목데이터가 같은 저장소에 섞인다.
  2. **삭제 무력화:** `settings`의 `clearData()`가 `regrip_sessions`만 지우므로, **다음 페이지 로드 시 `seedMockData`가 다시 목데이터를 채워 넣어** 초기화가 사실상 불가능하다.
  3. **어휘 불일치로 인한 매핑 실패:** 목 라벨은 `'완전 그립 훈련'·'핀치 그립 훈련'·'측면 그립 훈련'·'손가락 펴기'`(4종, `:262`)인데, 실제 게임 저장 라벨은 `'풍선 게임'·'크레인 게임'`이다. 따라서 `history.html`의 `exerciseIcons` 매핑(`:262-267`)이 실제 게임 라벨을 **찾지 못해 기본 아이콘으로 폴백**한다.

* **기술적 분석:**
  개발 편의용 시더가 **프로덕션 데이터 경로에 상주**하면서 데이터 무결성을 오염시키는 안티패턴이다. 특히 "삭제해도 되살아나는" 동작은 사용자에게 데이터 통제권을 주지 못하는 심각한 신뢰 문제이며, 개인정보(건강정보) 삭제 요구권과도 충돌한다. 라벨 어휘 불일치는 목 스키마와 실제 스키마가 **서로 다른 어휘 공간**에 있음을 드러낸다 — 이는 아이콘 폴백에서 그치지 않고, 향후 운동 유형별 통계·필터를 만들 때 전면적으로 깨질 지점이다.

* **통합 개선안:**
  1. **`seedMockData`를 자동 경로에서 제거.** `initPage()`에서 호출을 삭제하고, 데모가 필요하면 **명시적 트리거**(설정의 "데모 데이터 채우기" 버튼 → `seedDemoData()`)로만 실행한다(UX-4와 연동).
  2. **데모 데이터를 격리/라벨링:** 데모 세션에 `isDemo: true` 플래그를 부여해 실데이터와 구분하고, `clearData()`가 이를 완전히 제거하도록 한다. 실데이터와 절대 섞지 않는다.
  3. **라벨 어휘 통일:** 게임 저장 라벨과 아이콘 매핑을 **단일 카탈로그**(예: `game_type` 코드 → 표시명·아이콘)로 통일한다. 데모 데이터도 이 카탈로그의 라벨만 사용한다.

### 3.6 [DI-6 · High] 세트 상세를 매 열람마다 난수 재생성 — 재현 불가 · 정보 손실

* **논리적 충돌 및 간극:**
  `history.html`의 세션 상세는 세트별 reps/holdTime/force를 **저장된 값이 아니라 세션을 열 때마다 `Math.random`으로 즉석 생성**한다(`generateSetData`, `:242-252`). 따라서 **같은 세션을 다시 열면 값이 매번 달라진다.** 또한 크레인 게임의 `attempts`(시도 수)는 결과 화면에만 표시되고 **저장 스키마에 존재하지 않아** 영구 손실된다.

* **기술적 분석:**
  이는 두 개의 결함이다. (1) **재현 불가능성:** 재활 기록은 진행 추적이 목적인데, 열 때마다 바뀌는 값은 기록으로서 무의미하며 임상적으로 위험하다("지난주 3세트째 45%였다"가 열 때마다 달라짐). 데이터가 **영속화되지 않고 표시 시점에 조작(fabricate)**되는 근본적 무결성 위반이다. (2) **정보 손실:** 게임이 생성한 유의미한 지표(`attempts`)가 저장 스키마에 없어 버려진다 — 세션 스키마가 게임의 실제 산출을 온전히 담지 못한다.

* **통합 개선안:**
  1. **세트 상세를 게임 시점에 실제로 기록·저장.** 게임 루프가 세트별 실측(reps/holdTime/force)을 수집해 세션과 함께 저장한다. BE-4의 `session_sets` 테이블(1:N)로 영속화한다.
  2. **`generateSetData` 폐기.** 표시는 저장된 세트를 읽어 렌더한다.
  3. **세션 스키마 확장:** `attempts` 등 게임별 지표를 스키마에 포함(게임 유형별 확장 필드 또는 `metadata` JSONB)해 정보 손실을 제거한다.

### 3.7 [DI-7 · High] 캘리브레이션 결과 미저장 — 하드웨어 접점이 장식

* **논리적 충돌 및 간극:**
  `calibration.html`의 `captureBaseline()`(`:161-220`)은 `baseline0`/`baseline100`을 **지역 변수에만 보관**하고 어디에도 저장하지 않는다. `localStorage` 키 `regrip_calibration`은 **존재하지 않으며**, 게임들도 캘리브레이션 값을 참조하지 않는다. 게다가 라이브 미터는 `SensorService`가 아니라 화면 자체의 `Math.random`으로 그려진다(`:154-159`). 결과적으로 캘리브레이션 화면은 **UI 흐름만 있는 장식**이며, 화면을 완료해도 시스템에 아무 영향이 없다.

* **기술적 분석:**
  O2O 재활 제품에서 캘리브레이션은 **센서 원시 신호를 개인화된 0~100% 악력 스케일로 매핑하는 필수 절차**다. 사람마다·기기마다 FSR 응답이 다르므로, 캘리브레이션 없이는 모든 악력 수치의 절대적 의미가 사라진다. 그 결과가 저장되지 않고 게임이 참조하지도 않는다는 것은, **하드웨어와 소프트웨어를 잇는 접점 자체가 끊겨 있다**는 뜻이다(BE-2의 `connect()` 미호출과 같은 뿌리). 또 라이브 미터가 실제 센서가 아닌 난수라는 점은 이 화면이 실측을 전혀 보여주지 않음을 확증한다.

* **통합 개선안:**
  1. **캘리브레이션 결과 영속화:** `{ baselineMin, baselineMax, capturedAt }`를 `regrip_calibration`(로컬) / `calibrations` 테이블(서버, BE-4)에 저장한다.
  2. **게임이 캘리브레이션을 참조:** 게임 루프가 센서 원시값을 `baselineMin~baselineMax` 기준으로 0~100% 정규화해 사용한다(UX-2의 목표 악력 파라미터와 결합).
  3. **라이브 미터를 실제 센서에 연결:** `SensorService.onForceUpdate`를 구독해 실측을 표시하고, 미연결 시 명시적 시뮬레이션 표시(BE-3)로 폴백한다.
  4. **여정 편입:** 캘리브레이션을 온보딩/설정 경로에 배치(UX-5)해 도달 가능하게 만든다.

### 3.8 [DI-8 · 긍정] 세션 스키마는 생산-소비 간 일치

객관성을 위해 명시한다. **세션의 핵심 스키마 자체는 정합적이다.** 게임 저장 시의 `{ date, label, durationMin, sets, avgForce, maxForce, stars }`가 `seedMockData`가 생성하는 필드, 그리고 `history.html`이 소비하는 필드와 **일치**한다. 즉 데이터 모델의 골격은 존재하며, 문제는 골격의 부재가 아니라 **(a) 지표 파생 계산의 부재(DI-1~3), (b) 목데이터 오염(DI-5), (c) 세트 상세·게임별 지표의 영속화 부재(DI-6), (d) 캘리브레이션 접점 부재(DI-7)**다. 이는 곧 **세션 스키마를 SSOT로 삼아 그 위에 게이미피케이션 엔진과 세트 영속화를 얹으면 정합성이 회복 가능**함을 의미한다. 처음부터 다시 설계할 필요는 없다.

## 4. 프로젝트 성공을 위한 추가 권장 작업 (Actionable Next Steps)

아래는 **의존성과 위험을 반영한 실행 순서**다. 앞선 항목이 뒤 항목의 선결 조건이 되도록 배열했다. 각 항목은 "왜 지금", "무엇을", "기대 효과"를 명시한다.

### 1위. 단일 진실 소스(SSOT) 게이미피케이션 엔진 도입 + 목데이터 격리 — **즉시 착수**

* **무엇을:** 레벨·XP·연속출석·배지·진행률을 **세션 데이터에서 파생 계산**하는 `GamificationService`(순수 함수 계층)를 만들고, 10개 페이지의 인라인 상수(DI-1)를 전량 이 엔진 호출로 교체한다. XP 적립 규칙을 정의해 세션에서 XP가 발생하도록 하고(DI-3), `TIERS`/XP 곡선/업적 정의를 단일 모듈로 통합한다. 동시에 `seedMockData` 자동 호출을 제거하고 `seedDemoData()`로 명시적 트리거화하며 데모 데이터를 `isDemo` 플래그로 격리한다(DI-5).
* **왜 지금(실행 이유):** 이것은 제품의 **핵심 가치 명제("게임 → 재활 성과 성장")를 코드로 성립시키는 최소 요건**이다. DI-1·2·3의 Critical/High가 모두 여기서 해소되며, 이후 모든 화면·백엔드 작업이 이 SSOT 위에서 정의된다. 지금 잡지 않으면 화면을 그릴수록 모순이 늘어난다.
* **기대 효과:** 페이지 간 수치 모순 원천 제거, 게임 결과가 실제로 지표에 반영되는 인과 루프 확립, 이후 백엔드가 그대로 미러링할 계산 규칙 확보. **데모에서 제품으로의 전환점.**

### 2위. 백엔드 MVP 착수 전 설계 확정 (권위·정합성 계층)

* **무엇을:** `docs/backend/00~07` 설계서를 기준으로 **PostgreSQL 모놀리식 + JWT 인증**을 확정하고, 핵심 계약을 못 박는다 — (a) 세션 저장을 `INSERT session → xp_ledger → achievements` **단일 트랜잭션**으로, (b) **멱등키**로 중복 제출 방지, (c) `stars`·XP를 **서버가 재계산**(클라 값 불신), (d) 아바타는 오브젝트 스토리지로 분리해 DB엔 URL만, (e) 건강정보 동의·보호 조치 반영. 클라이언트 `DataService`를 단일 게이트웨이로 정리하고 공통 fetch 래퍼(인증/에러/타임아웃/멱등)를 도입한다(BE-1).
* **왜 지금:** 게이미피케이션의 **권위(authority)가 클라이언트에 있으면 치팅과 정합 붕괴가 불가피**하다(BE-4 Critical). 1위에서 만든 계산 규칙을 서버 권위로 승격해야 값이 신뢰 가능해진다. 트랜잭션 경계 없이 구현을 시작하면 섹션 3의 모순이 서버에서 재생산된다.
* **기대 효과:** 데이터 무결성·치팅 방지·기기 간 정합 확보, 개인정보 규제 리스크 선제 관리, 프론트-백 계약 확정으로 병렬 개발 가능.

### 3위. 접근성 · 임상 UX 정비

* **무엇을:** WCAG AA 명암비 충족(토큰 재조정), 전역 `:focus-visible`, `prefers-reduced-motion` 대응, 터치 타깃 44pt, `div onclick` → 시맨틱 요소, 네이티브 `confirm()` 교체(UX-3). **풍선 게임 게이지-물리 평형점 정합**(단일 파라미터 파생, UX-2)과 캘리브레이션 결과 게임 반영(DI-7)을 포함한다.
* **왜 지금:** ReGrip은 **재활 의료 인접 서비스**이며 타깃 사용자에 고령·저시력·전정장애·손기능 저하자가 포함된다. 접근성 결함은 곧 **핵심 사용자 배제**이고, 잘못된 힘 피드백은 **임상 안전 문제**다. 규제·임상 신뢰성과 직결되므로 MVP 전 필수다.
* **기대 효과:** 타깃 사용자 포용, 임상적으로 올바른 훈련 피드백, 접근성 규제 대응, 제품 신뢰도 상승.

### 4위. E2E 스모크 자동화 + CI

* **무엇을:** Playwright로 핵심 시나리오를 자동화한다 — **게임 플레이(시뮬레이션 입력) → 홈·기록·업적·프로필 4페이지의 지표가 일관되게 반영되는지 assert**(DI-1·2의 회귀 방지), **빈 상태에서 콘솔 에러 0**(UX-4), 탭 전환 상태(UX-1) 등. axe-core 접근성 린트(UX-3)를 파이프라인에 포함하고 CI에 연결한다.
* **왜 지금:** 1~3위에서 정합성을 회복한 뒤, 그것이 **다시 깨지지 않도록 고정**해야 한다. ReGrip의 시뮬레이션 우선 설계(1.6) 덕에 하드웨어 없이 E2E가 가능하다는 강점을 활용한다.
* **기대 효과:** 지표 정합성·빈 상태·접근성의 회귀를 자동 차단, 리팩터링 안전망 확보, 릴리스 신뢰도 상승.

### 5위. 부하·보안 검증 — 백엔드 구현 후 (시기 명시)

* **무엇을:** k6로 **세션 제출 피크 시나리오** 부하 테스트(트랜잭션·멱등 경로의 처리량/지연 검증), 개인정보 영향평가(건강정보 수집·저장·삭제의 동의 플로우 및 보호 조치 점검), 보안 리뷰(인증·인가·저장 데이터 보호).
* **왜 지금이 아니라 나중인가:** 부하·침투 대상인 **백엔드가 아직 없다.** 2위에서 백엔드가 구현된 **후에** 실측 대상이 생긴다. 지금 착수하면 대상 없는 낭비다. 단, 개인정보 처리 방침 설계는 2위와 동시에 시작한다.
* **기대 효과:** 실사용 트래픽 대비 안정성 확보, 건강정보 규제 준수 입증, 출시 전 보안 취약점 제거.
