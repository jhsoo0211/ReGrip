# 04. 센서 데이터 처리 정책

> **한 줄 요약**: 센서 실시간 데이터는 **클라이언트가 로컬에서 처리**하고, 서버는 **세션 요약만** 수신한다. 실시간 스트리밍 인프라는 짓지 않는다. 임상용 원시 시계열 계약은 Stage 3에서 "세션 종료 후 배치 업로드"로만 연다.

## ADR-04-1: 센서 실시간 데이터는 로컬 처리, 서버는 세션 요약만 수신

### 배경(Context)

FSR 악력 센서는 Arduino/RPi에서 로컬 WebSocket(`ws://localhost:8080`)으로 `{force: 0~100, timestamp}`를 약 20Hz(설계상 최대 30~60Hz까지 가능)로 브라우저에 흘려보낸다. 브라우저 게임 루프(`requestAnimationFrame`)가 이 값을 받아 풍선/크레인을 실시간으로 움직인다. 센서와 브라우저는 **같은 로컬 네트워크**에 있다.

질문: 이 고빈도 스트림을 서버로 보내야 하는가?

### 결정(Decision)

**보내지 않는다.** 센서 실시간 데이터는 브라우저에서 로컬로 처리하고, 서버에는 **세션이 끝난 뒤 요약 1건**(`avgForce`, `maxForce`, `score`, `durationSec`, 그리고 1Hz로 다운샘플한 `force_series`)만 제출한다([02](./02-api-spec.md) `POST /users/me/sessions`).

### 근거(Why)

**① 게임 루프가 rAF + 로컬 WS다 — 서버 왕복은 게임성을 훼손한다.**
게임 반응성은 밀리초 단위다. 센서→서버→브라우저 왕복을 넣으면 인터넷 지연·변동이 게임 조작감에 직접 얹힌다. 로컬 WS는 지연이 거의 없다. 실시간 경로에 서버를 끼우는 것은 손해만 있다.

**② 30~60Hz × 15분 = 수만 샘플/세션 — 초기 규모에 스트리밍 인프라는 낭비다.**
한 세션이 수만 개 샘플을 만든다. 이를 실시간으로 받으려면 WebSocket 게이트웨이, 백프레셔 처리, 세션별 스트림 관리, 대용량 시계열 저장이 필요하다. 유저 수십~수천 명, 세션 쓰기 초당 1건 미만([00](./00-overview.md))인 규모에서 이 인프라는 정당화되지 않는다.

**③ 오프라인 내성이 재활 환경의 실제 요구다.**
센서와 브라우저가 같은 로컬망에 있으므로 **인터넷 없이도 훈련이 가능해야 한다**(가정/시설에서 네트워크가 불안정할 수 있다). 로컬 처리 모델에서는 인터넷이 끊겨도 훈련을 마치고, 세션 요약을 **나중에 제출**하면 된다. 멱등키(`clientSessionId`)가 오프라인 큐 재전송을 안전하게 만든다([00](./00-overview.md) 원칙 ②).

### 기각된 대안(Rejected)

- **실시간 센서 스트리밍(서버가 모든 프레임 수신)**: 게임성 훼손(①), 인프라 과설계(②), 오프라인 불가(③). 초기 규모에서 얻는 것이 없다.
- **서버 사이드 게임 시뮬레이션(치팅 방지 목적)**: FSR 원시 측정치 위변조는 어차피 완전 차단 불가([03](./03-gamification-engine.md) §7.1)하므로, 실시간 검증을 위한 스트리밍은 비용만 크고 목적을 달성하지 못한다.

## ADR-04-2: force_series는 1Hz 다운샘플만 저장

### 결정(Decision)

세션 요약에 포함하는 `force_series`(추이 그래프용)는 **1Hz로 다운샘플**한 배열만 `sessions.force_series jsonb`에 저장한다. 원시 30~60Hz는 저장하지 않는다.

### 다운샘플 스펙

- 클라이언트가 세션 동안 수집한 고빈도 샘플을 **1초 단위 대표값**(해당 1초 구간의 평균 또는 피크)으로 축약한다.
- 15분 세션 → 약 900개 포인트. `jsonb` 배열로 충분히 가볍다.
- 저장 목적은 세션 상세 화면의 **추이 그래프**([02](./02-api-spec.md) `GET .../sessions/{id}`의 `forceSeries`)와 요약 통계 검증이다.
- 예: `"forceSeries": [40, 42, 45, 41, 38, ...]` (인덱스 = 경과 초).

### 근거(Why)

1Hz면 추이 시각화·요약에 충분하고, 원시 대비 저장량이 수십 분의 1이다. 원시 시계열은 임상적 재분석이 필요할 때만 의미가 있는데, 그 요구(B2B 임상 계약)는 아직 없다.

### 기각된 대안(Rejected)

- **원시 전량 저장**: 로우/저장 팽창, 조회 시 대용량 페이로드. 이득은 임상 재분석뿐인데 그 계약이 아직 없다.
- **아무 시계열도 저장 안 함(요약 스칼라만)**: 추이 그래프를 못 그린다. 1Hz는 그 최소 비용의 절충.

## ADR-04-3: 임상용 원시 시계열은 Stage 3에서 배치 업로드로만

### 결정(Decision)

B2B 임상 요구가 실제로 생기면(치료사가 원시 파형 분석을 계약으로 요구), **실시간이 아니라 세션 종료 후 압축 배치 업로드**로 원시 샘플을 받는다.

```
POST /api/v1/users/me/sessions/{id}/raw-samples
Content-Type: application/octet-stream (또는 gzip 압축 바이너리)
```

- 세션이 이미 저장된 뒤, 원시 샘플을 별도 요청으로 첨부한다.
- 저장은 **S3 호환 오브젝트 스토리지의 압축 파일** 또는 **TimescaleDB**로([05](./05-scaling-roadmap.md) Stage 3). 관계형 코어 테이블에는 넣지 않는다.
- 이 경로도 **실시간 스트리밍이 아니다** — ingest 경로만 분리하며 MSA로 가지 않는다.

### 근거(Why)

임상 재분석은 실시간성이 필요 없다(사후 분석). 배치 업로드는 게임성·오프라인 내성을 해치지 않으면서 원시 데이터를 확보한다. 요구가 확정되기 전에는 저장하지 않아 비용·규제 노출을 줄인다.

### 기각된 대안(Rejected)

- **처음부터 원시 시계열 파이프라인 구축**: 요구가 확정되지 않은 기능에 인프라 선투자 — 과설계([05](./05-scaling-roadmap.md) 과설계 금지 목록).
- **실시간 스트리밍으로 원시 수집**: ADR-04-1의 이유로 기각.

```
[FSR 센서 20~60Hz] --ws://localhost:8080--> [브라우저 게임 루프(rAF, 로컬 처리)]
                                                     |
                                    세션 종료 시 요약 계산(avg/max/score/1Hz series)
                                                     |
                              POST /users/me/sessions (요약 1건, clientSessionId 멱등)
                                                     |
                                              [ReGrip 백엔드 = 요약만 저장]

(Stage 3, 임상 계약 시에만)
  세션 저장 후 --> POST .../sessions/{id}/raw-samples (압축 배치) --> 오브젝트 스토리지/TimescaleDB
```
