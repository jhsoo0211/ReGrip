# 06. 보안 / 규제 준수

> **한 줄 요약**: 재활 측정 데이터는 개인정보보호법상 **민감정보(건강정보)**다. 별도 민감정보 처리 동의(항목·목적·보유기간)를 받고, 의료법상 진단·처방을 표방하지 않으며("훈련 보조" 포지셔닝), 저장은 암호화·해시·접근 감사·soft delete 파기 원칙으로 다룬다.

## 관련 문서
- 설계 원칙 ④(민감정보 최소 수집): [00-overview.md](./00-overview.md)
- 암호화 컬럼(`phone_enc`, `password_hash`)·동의(`consent_at`): [01-erd.md](./01-erd.md)
- 인증(JWT/Refresh)·회원가입 동의 필드: [02-api-spec.md](./02-api-spec.md)

> 면책: 이 문서는 설계 지침이며 법률 자문이 아니다. 실제 서비스 전 개인정보·의료 분야 전문 법률 검토를 반드시 받는다.

## 1. 법적 성격 규정

### 1.1 민감정보(건강정보) 해당

재활 악력 측정 데이터, `injury_type`(부상 유형), 세션 데이터는 **개인정보보호법 제23조의 민감정보(건강에 관한 정보)**에 해당한다. 민감정보는 일반 개인정보보다 강한 보호가 요구된다.

> **결정(Decision)**: `injury_type`과 세션 측정 데이터를 민감정보로 분류하고, 수집 시 **별도 민감정보 처리 동의**(일반 개인정보 동의와 구분)를 항목·목적·보유기간을 고지하여 받는다.
>
> **근거(Why)**: 건강정보는 법상 별도 동의 대상이다. 일반 동의에 묶어 받으면 무효 소지가 있고 유출 시 책임이 가중된다. 동의 없이 수집·처리하면 위법.
>
> **기각된 대안(Rejected)**: 일반 개인정보 동의에 포괄 — 민감정보 별도 동의 요건 미충족, 법적 리스크.

**동의 항목 명세(회원가입 시 고지)**
- **처리 항목**: 부상 유형, 악력 측정값(세션), 훈련 이력.
- **처리 목적**: 재활 훈련 보조·진행 추이 제공, 게이미피케이션.
- **보유 기간**: 회원 탈퇴 시까지(탈퇴 후 파기 원칙은 §5). 비식별 통계는 별도 고지.

### 1.2 의료법 — 진단·처방 표방 금지

> **결정(Decision)**: 서비스는 **진단·처방·치료 효과를 표방하지 않는다.** "훈련 보조(rehabilitation training aid)"로 포지셔닝한다. B2B에서도 병원 진료 데이터를 수신하지 않고, **자사 측정 데이터만 치료사에게 단방향 제공**한다.
>
> **근거(Why)**: 의료 진단·처방은 의료법상 의료인·의료기관의 영역이다. 앱이 이를 표방하면 무면허 의료행위·의료기기 규제 리스크가 생긴다. "훈련 보조" 포지셔닝과 단방향 데이터 제공으로 이 경계를 지킨다.
>
> **기각된 대안(Rejected)**: "재활 진단/치료" 마케팅 — 의료법 위반 소지. 병원 EMR 연동으로 진료 데이터 수신 — 의료정보 취급 규제 부담 급증.

`profiles.doctor_name`은 B2C의 자유 입력 참고 필드로만 존치하며, 이는 진료 연동이 아니다([01](./01-erd.md)).

## 2. 저장 시 보호 조치

| 대상 | 조치 |
|------|------|
| 비밀번호 | **argon2id** 해시(솔트·메모리 하드). 평문·역산 불가. |
| 전화번호 | **애플리케이션 레벨 암호화**(AES-GCM 또는 `pgcrypto`). `profiles.phone_enc bytea`. |
| 아바타 | base64 컬럼 금지 → **오브젝트 스토리지 + presigned URL**. |
| 전송 구간 | 전 구간 **TLS**. |

### 2.1 아바타: base64 → 오브젝트 스토리지 + presigned URL

> **결정(Decision)**: `avatarBase64`(data URL)를 DB에 저장하지 않고, 오브젝트 스토리지에 업로드 후 **presigned URL**로 서빙한다([01](./01-erd.md) profiles, [02](./02-api-spec.md) §3.2 과도기 호환).
>
> **근거(Why)**: base64를 DB에 넣으면 로우 비대·조회 비용·백업 팽창이 생기고, 공개 버킷은 무단 접근 위험이 있다. presigned URL은 만료 시간이 있는 서명 링크로 접근을 통제한다.
>
> **기각된 대안(Rejected)**: base64 DB 저장 — 성능·백업 문제. 공개 버킷 직접 서빙 — 접근 통제 불가.

### 2.2 전화번호: 애플리케이션 레벨 암호화

> **결정(Decision)**: 전화번호는 애플리케이션 레벨에서 AES-GCM(또는 `pgcrypto`)으로 암호화해 `bytea`로 저장하고, 응답 시 복호화한다.
>
> **근거(Why)**: 전화번호는 개인 식별성이 높다. DB 덤프·백업 유출 시에도 키 없이는 복호화 불가하게 만든다. 애플리케이션 레벨 암호화는 DB 관리자조차 평문을 못 보게 한다.
>
> **기각된 대안(Rejected)**: 평문 저장 — 유출 시 즉시 노출. DB 전체 암호화(TDE)만 — DB 접근 권한자에겐 평문 노출.

## 3. 인증·접근 통제

- **argon2id** 비밀번호 해시(§2).
- **JWT 키 회전**: 서명 키를 주기적으로 회전하고, 회전 시 기존 토큰을 유예 기간 후 무효화.
- **Refresh 토큰 회전·폐기**: [02](./02-api-spec.md) §2.
- **CORS 화이트리스트**: 허용된 오리진만. 와일드카드(`*`) 금지.

## 4. 만 14세 미만 법정대리인 동의

> **결정(Decision)**: `birth_date`로 만 14세 미만을 판별하고, 미만이면 **법정대리인 동의**를 필수로 받는다(회원가입 `consents.guardianConsent`, [02](./02-api-spec.md) §2.3).
>
> **근거(Why)**: 개인정보보호법상 만 14세 미만 아동의 개인정보 수집은 법정대리인 동의가 필요하다. 재활 대상에 아동이 포함될 수 있으므로 판별·동의 절차를 둔다.
>
> **기각된 대안(Rejected)**: 연령 무관 자기 동의만 — 아동 가입 시 위법.

## 5. B2B 열람 인가 + 감사 로그

### 5.1 동의 없는 열람 차단

> **결정(Decision)**: 치료사가 환자 데이터를 열람하려면 `care_relations`가 **`status='active'` 그리고 `consent_at IS NOT NULL`**이어야 한다. 조건 미충족 시 **403 Forbidden**을 반환하고, 모든 열람 시도(성공·실패 포함)를 `audit_logs`에 남긴다.
>
> **근거(Why)**: 환자의 명시 동의 없는 건강정보 열람은 위법이다. 동의를 컬럼(`consent_at`)으로 물화하고 인가 로직이 이를 강제 참조하게 하면, 코드가 동의 없는 접근을 구조적으로 막는다. 감사 로그는 사후 추적·책임 규명 근거다.
>
> **기각된 대안(Rejected)**: 관계 존재만으로 열람 허용 — 동의 없는 접근 발생. 감사 로그 없음 — 부적절 접근 추적 불가.

### 5.2 audit_logs 테이블

```sql
CREATE TABLE audit_logs (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  actor_id   uuid NOT NULL,              -- 열람 시도자(치료사)
  patient_id uuid NOT NULL,              -- 열람 대상 환자
  action     text NOT NULL,             -- 'view_sessions' | 'view_profile' | 'create_prescription' ...
  result     text NOT NULL DEFAULT 'allowed'  -- 'allowed' | 'denied'
             CHECK (result IN ('allowed','denied')),
  at         timestamptz NOT NULL DEFAULT now(),
  meta       jsonb                       -- IP, 대상 리소스 등
);
CREATE INDEX idx_audit_patient_at ON audit_logs (patient_id, at DESC);
CREATE INDEX idx_audit_actor_at ON audit_logs (actor_id, at DESC);
```

B2B 환자 데이터 접근은 **전건 audit** 대상이다([07](./07-b2b-extension.md)).

## 6. 탈퇴·파기 정책

> **결정(Decision)**: 탈퇴는 **soft delete로 즉시 접근 차단**(`users.status='deleted'`, `deleted_at` 세팅) 후 **30일 경과 시 개인정보 파기 배치**. 통계는 **비식별화하여 보존**하되, 이 처리 방식을 **동의 문구와 정확히 일치**시킨다.
>
> **근거(Why)**: 즉시 하드 삭제는 오조작·복구 요청·정산/감사 필요를 감당하지 못한다. soft delete로 즉시 접근을 끊어 실질 보호를 하고, 유예 후 파기한다. 통계 비식별 보존은 서비스 개선에 필요하나, 반드시 동의 고지 내용과 일치해야 적법하다(고지와 다른 처리는 위법).
>
> **기각된 대안(Rejected)**: 탈퇴 즉시 완전 삭제 — 오조작·감사 요구 대응 불가. 개인 식별 데이터를 통계로 무기한 보존 — 동의 범위 초과 시 위법.

**파기 배치 대상**: 프로필 식별정보, `phone_enc`, `avatar_url`(스토리지 객체 포함), 세션의 식별 연결. 비식별 통계(개인 식별 불가 집계)는 동의 고지에 명시한 범위에서 보존.
